# 5.7. Seguridad del Sistema

---

## 1. Protección de Contraseñas

Las contraseñas de los usuarios son el elemento más sensible del sistema. Por esta razón, nunca se almacenan en su formato original. En su lugar, se aplica un proceso de transformación (hash) que convierte la contraseña en una cadena de caracteres irreconocible. Cuando un usuario inicia sesión, el sistema aplica el mismo proceso a la contraseña ingresada y compara el resultado con el almacenado. De esta forma, incluso si alguien accediera a la base de datos, no podría conocer las contraseñas reales.

Durante el registro, el sistema exige que la contraseña tenga al menos 6 caracteres. Al cambiar la contraseña, el requisito mínimo aumenta a 8 caracteres y se muestra un indicador visual que ayuda al usuario a evaluar la fortaleza de su nueva contraseña. Este indicador considera la longitud, el uso de mayúsculas, minúsculas, números y símbolos, clasificando la seguridad en cinco niveles desde muy débil hasta muy fuerte.

---

## 2. Prevención de Accesos No Autorizados

El sistema garantiza que cada estudiante solo pueda ver y gestionar sus propias tareas. Cuando un usuario inicia sesión, el sistema registra su identidad y todas las operaciones posteriores están limitadas exclusivamente a las tareas que le pertenecen. Es imposible que un usuario acceda a las tareas de otro compañero, incluso si intentara manipular la información.

Además, el inicio de sesión no revela si el error está en el carné o en la contraseña. Simplemente muestra un mensaje genérico de "carné o contraseña incorrectos", evitando que un atacante pueda identificar qué usuarios existen en el sistema.

---

## 3. Protección contra Inyección de Código en Base de Datos

Todas las consultas que el sistema envía a la base de datos utilizan un mecanismo que separa claramente el comando SQL de los datos ingresados por el usuario. Esto evita que alguien pueda insertar comandos maliciosos a través de los campos de texto, una técnica conocida como inyección SQL. Cada valor ingresado por el usuario se trata como dato, no como parte de la instrucción SQL.

---

## 4. Almacenamiento Seguro de Credenciales

La información necesaria para conectar con la base de datos (servidor, nombre de la base, usuario y contraseña) no está escrita directamente en el código del programa. En su lugar, se almacena en un archivo de configuración separado que no se incluye cuando se comparte el código fuente. Esto permite que cada instalación del sistema tenga sus propias credenciales sin riesgo de exponerlas públicamente.

---

## 5. Confirmación de Acciones Importantes

El sistema siempre solicita una confirmación antes de ejecutar acciones que no se pueden deshacer fácilmente o que implican pérdida de datos:

- Al eliminar una tarea, se muestra una advertencia de que la acción es permanente.
- Al deshacer una acción, se pide confirmación para evitar revertir accidentalmente.
- Al cerrar sesión, se pregunta si el usuario está seguro de querer salir.

Esto previene errores causados por clics accidentales y da al usuario la oportunidad de reconsiderar su decisión.

---

## 6. Copias de Seguridad para Deshacer

El sistema implementa una funcionalidad de deshacer que permite revertir la última acción realizada. Para que esto sea seguro, cada vez que se guarda una acción en el historial, se almacena una copia completa e independiente del estado de la tarea en ese momento. Esto significa que, aunque la tarea original se modifique después, la copia guardada permanece intacta y puede usarse para restaurar el estado anterior sin problemas.

Las acciones que se pueden deshacer incluyen la creación de tareas, la edición de sus datos y el marcarlas como completadas.

---

## 7. Manejo de Errores

Todas las operaciones que involucran la base de datos están protegidas contra fallos. Si ocurre un error (por ejemplo, si la base de datos no está disponible), el sistema lo detecta y maneja la situación de forma controlada. En lugar de mostrar mensajes técnicos confusos, la aplicación responde con mensajes amigables o, en caso extremo, puede operar con datos de ejemplo para no dejar al usuario sin herramienta.

Los detalles técnicos de los errores se registran internamente para facilitar la depuración, pero nunca se muestran al usuario final.

---

## 8. Validación de Datos Ingresados

Todas las ventanas del sistema que reciben información del usuario validan los datos antes de procesarlos. Esto incluye:

- Verificar que los campos obligatorios no estén vacíos.
- Comprobar que las fechas ingresadas sean válidas.
- Asegurar que los números ingresados (como días a simular) sean positivos.
- Confirmar que las contraseñas cumplan con la longitud mínima.
- Verificar que las confirmaciones de contraseña coincidan.

Esta validación ocurre tanto en la interfaz como antes de enviar los datos a la base de datos, proporcionando una doble capa de protección.

---

## 9. Separación de la Interfaz y los Datos

La arquitectura del sistema separa claramente la interfaz de usuario de la lógica de negocio y del acceso a datos. Las ventanas visuales nunca se comunican directamente con la base de datos; siempre lo hacen a través de capas intermedias que aplican las validaciones y reglas correspondientes. Esto evita que un error en la interfaz pueda comprometer la integridad de los datos almacenados.

---

## 10. Resumen de Medidas de Seguridad

| Medida | Descripción |
|---|---|
| Contraseñas protegidas | Se almacenan transformadas mediante un algoritmo irreversible |
| Aislamiento de datos | Cada usuario solo accede a sus propias tareas |
| Consultas seguras | Los datos ingresados nunca se mezclan directamente con las instrucciones SQL |
| Credenciales externas | Los datos de conexión están en un archivo separado del código |
| Confirmaciones | Las acciones destructivas siempre requieren confirmación explícita |
| Copias de seguridad | El historial de deshacer almacena copias independientes de cada tarea |
| Tolerancia a fallos | Los errores se manejan sin mostrar información técnica al usuario |
| Validación de entrada | Todos los campos se verifican antes de procesarlos |
| Arquitectura en capas | La interfaz no accede directamente a los datos |
